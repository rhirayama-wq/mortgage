# 長期機能マップ — Loan Checker × モゲチェック 融合

> **文書の性格**: 本書は要件定義書 §8 が要求する「開発前の機能調査・分類表」である。
> 目的は、最終ゴール（不動産事業者向け業務支援＋購入者向け診断・比較・申込支援の融合）へ
> 拡張できる設計を保ちつつ、各機能を `MVP` / `Post-MVP` / `Final Goal` に分類し、
> **現在のスコープ（Phase 1 = 認証・所属・RLS・監査）を無秩序に拡大しない**ことにある。
>
> **重要な制約（要件定義書より）**
> - TERASS / MFS の**非公開情報・営業秘密・内部仕様・著作物・画面・ソースコードは推測も複製もしない**。
> - 下表の「出所」列で、公開情報で確認できたものと、未確認・推測にすぎないものを厳密に区別する。
> - 「全機能」を、確認していない機能まで想像で埋めない。
> - 競合分析は**機能・課題・ワークフローの抽象化**に限定し、本プロダクト独自のUI・データモデル・判定ロジックを設計する。

## 調査サマリ（2026-07-24 時点の公開情報）

### A. TERASS「Loan Checker」— 不動産事業者向け（公開情報で確認できた範囲）
- 40以上の金融機関の住宅ローン商品を1画面で横断検索。
- 顧客属性＋物件条件に合わせた最適商品の抽出・提案。
- 多様な顧客属性への対応（LGBTQ、非永住外国籍等の非典型プロファイルを公開文で明示）。
- 複数商品の並列比較。
- 提携銀行の優遇金利提供。
- 提案書・資金計画書の自動生成（有償機能）。
- 不動産会社が自社の銀行提携条件を組み込めるカスタマイズ（有償）。
- ワークフローは「検索 → 精査 → 提案生成」の3ステップ。基本検索は無償、提案書・カスタマイズは有償。
- 登録ユーザー5,000人突破の実績（規模の公開指標）。
- **公開情報で確認できないもの**: 内部の判定ロジック、金融機関別の非公開相談ポイント、審査実績データ、画面詳細仕様 → **推測・複製しない**。

### B. MFS「モゲチェック」— 購入者向け（公開情報で確認できた範囲）
- 無料・約5分・その場でわかる住宅ローン診断。
- おすすめランキング（変動 / 10年固定 / 20年固定 / 35年固定・フラット35 で別建て）。
- シミュレーション: 毎月返済額 / 借入可能額 / 借り換えメリット額。
- モゲチェック特別金利（通常金利から優遇、直接申込では得られない条件）。
- **プレ審査**: 30万人超のユーザーから独自収集した審査結果データで、申込前に承認可能性をリアルタイム推定。「審査結果を約束するものではない」と明示。公開時点では対応行が限定的（PayPay銀行）と報道。
- 審査支援（最短数分の事前審査体験）、申込導線。
- AIによる最適化された診断コメント（AI化第二弾）、AIアドバイザー。
- マガジン（金利・団信等の解説）、アプリ、メッセージ相談。
- **公開情報で確認できないもの**: 承認確率モデルの内部仕様、金融機関別の非公開審査基準、収集データの内部構造 → **推測・複製しない**。

## MVP（今回目指す最小業務価値）に**含める**機能の要約
認証・所属・ロール・RLS・監査（Phase 1）／匿名案件と顧客・収入・借入・物件・希望条件の入力（Phase 2）／
共通マスタ＋法人オーバーレイ、ルールベース適合判定（A1–A5, B4, B8–B10, B16）、月・総返済額計算、検索結果スナップショット保存と再現、
管理機能（マスタ・バージョン公開・CSVプレビュー確定・法人設定・ユーザー管理・監査ログ閲覧）。

## MVP に**含めない**（Post-MVP / Final へ送る）機能の要約
機械学習による承認確率推定、モゲチェックプレ審査の本番連携、本番事前・正式審査申込、金融機関API連携、
書類アップロード/OCR、電子契約、融資実行管理、高度な提案書・資金計画書自動生成、顧客セルフサービス完全版、
AIアドバイザー、審査実績学習モデル、金融機関メッセージング、借り換え継続モニタリング、金利変動通知、
CAPS等本番連携、信用情報機関データ、実在金融機関の非公開審査条件、他社製品の非公開機能の推測実装。

## 将来拡張のために MVP で**構造として確保する**境界（過度に複雑化しない範囲で）
B2B/B2C画面分離（route group）／申込・審査ステータス連携の余地／ルール判定と確率モデルの併用余地／
提案書・書類・専門家相談・審査フィードバック・AIアドバイス・借り換えフォロー・複数法人/ブランド展開。

## トレーサビリティ（バックログ運用ルール）
各機能は `MVP` / `Post-MVP` / `Final Goal` のラベル、対応ユーザー課題、業務フロー、依存関係、検証指標を持つ。
実装中に新候補が見つかっても即実装せず、①中核仮説に必要か ②MVP受入条件に含まれるか ③セキュリティ/整合性に必須か
④今やらないと大きな手戻りか ⑤後続へ安全に送れるか、の順で判断し、不要なら Post-MVP へ送る。
